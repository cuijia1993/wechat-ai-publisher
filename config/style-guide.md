# 智效进化论写作规范

## 读者与语气

- 面向会被 AI 影响工作、钱包、安全、健康、家庭和日常选择的普通人，不要求了解模型、编程或具体工具。
- 结论克制、明确，先给问题和结果，再解释过程。
- 不把 AI 描述成万能工具，必须说明失败、限制和人工确认点。
- 像一个靠谱同事在午饭时分享经验：直接、口语化、有细节，不使用讲师腔、论文腔或营销腔。
- 专有名词第一次出现时用日常语言解释；能说“让 AI 帮你整理会议待办”，就不先说“Agentic Workflow”。

## 传播原则

- 标题负责打开，证据负责信任，模板负责收藏，观点负责转发。
- 每篇只解决一个具体、高频且有实际代价的问题，不写宽泛综述。
- 标题优先使用“普通人场景 + 与钱/工作/安全/健康/家庭有关的后果 + 信息差”，工具和版本只作为正文证据。
- 执行“3 秒点击门槛”：不了解任何技术背景的人也能立刻看懂“这事为什么和我有关”。
- 标题先制造具体疑问，不先讲行业趋势；优先回答“会不会影响我、家人或钱包”。
- 新号文章必须指定一个 2～24 字的主搜索词，并在标题中原样包含；空格与大小写可忽略。
- 主搜索词优先使用近期产品、功能、政策或用户会主动输入的具体问题，禁止只用“AI”“效率”等宽泛词。
- 标题同时服务搜索与点击，使用“明确搜索实体 + 用户冲突/收益”，不能只追求情绪钩子。
- 开头 100 字内说清问题、实际代价和阅读收益。
- 开头根据证据选择最自然的入口：真实细节、关键数字、读者问题、操作现场或有记录的人物场景均可，不强行虚构“小林”“小王”。
- 新闻与事件解读优先从来源中最反常识、最有后果的事实切入；只有人物经历确实帮助解释问题时才使用故事开场。
- 禁止用“随着技术发展”“在当今时代”等空泛背景开场。
- 每段控制在手机端 2～4 行，多用步骤、对比、失败样本和检查清单。

## 结构选择

- 不使用固定七段式。根据内容选择一种主结构，通常安排 3～5 个章节：
  - 事件解读：关键事实 → 与读者的关系 → 边界 → 现在能做什么；
  - 操作复盘：原始任务 → 实际操作 → 出错细节 → 修正办法；
  - 问题判断：具体疑问 → 正反证据 → 作者判断 → 适用条件；
  - 方法教程：原始输入 → 关键步骤 → 失败样本 → 可复用方法。
- 故事、步骤、对比、清单和模板都是可选模块，不要求每篇全部出现。
- 一篇文章通常只保留一个主要可复制资产；没有真正可复用内容时，不为了“收藏价值”硬加清单。
- 小标题服务内容，不追求字数、句式和数量对称；连续使用“第一个、第二个、第三个”时，应确认编号本身确有必要。
- 正文不生成“文章阅读地图”或章节目录卡，直接进入内容。

教程、实测和提效案例必须展示真实输入、操作过程、失败或限制，不能只展示成功结果。
新闻解读和观点文章应展示具体来源细节、证据边界及推导过程，不强制添加输入输出示例。
故事不能冒充真实经历：真实案例需有记录，虚构或组合场景必须明确标注；能直接用事实讲清楚时，不新增虚构人物。
结尾给出下一步行动和一个具体讨论问题，不机械索要点赞转发。

## 反模板化

- 宁可保留自然的长短变化，也不要把每段修成相同节奏；允许一两句短促判断，也允许必要的长句完整交代条件。
- 不连续使用“问题是”“更稳妥的做法是”“值得注意的是”“真正重要的是”等总结句式。
- 不在每节末尾强行收束成金句，不把同一个观点换词重复三遍。
- 少用抽象正确话，优先写来源原话、界面文案、数字、动作和可观察后果。
- 作者要做取舍：解释最关键的两三点即可，不为显得完整硬拆成五点或七点。

## AI 价值增量

- 提效案例必须把 AI 放在真正费时、费脑或容易遗漏的环节，不能让人先完成信息提取、判断、分类和结构化，再让 AI 只负责润色。
- 示例输入保留原始形态，例如零散日历、任务记录、聊天片段、文档修改和相互冲突的状态；不得为了方便展示而预先整理成目标答案。
- 示例必须展示 AI 的中间产物：提取了什么、依据哪条记录、合并了哪些重复项、哪些内容存在歧义、需要人确认什么。
- 人负责确认事实、取舍、风险和承诺，但不应重新执行 AI 声称替代的全部整理工作。
- 使用“删除 AI 测试”：删掉 AI 步骤后，如果人已经拥有接近最终成品的内容和结构，说明 AI 没有产生实质增量，案例不得通过审查。
- AI 只改善措辞或排版时，必须如实定位为“写作辅助”，不能宣传为信息整理、决策或流程提效。

## 选题标准

- 优先选择同时具备“三强”的主题：强情绪（焦虑、冲突、损失、风险或反常识）、强利益（省钱、省时、避坑、增收或减少返工）、强实用（步骤、清单、模板或判断标准）。
- 重点方向：工作与收入、钱与消费、隐私与诈骗、健康与养老、孩子与教育、关系与情绪、旅行与日常决策。
- 本项目核心切口是“一个大众问题 + AI 带来的新变化 + 普通人的损失/收益 + 风险避坑”，优先选择有近期热点、真实或明确标注的组合案例、可执行结论的主题。
- 技术名词、模型名、版本号、框架名和产品功能不得作为默认选题入口，只能作为正文中的事实、案例或变化来源。
- 会议、文档、邮件、表格、自动化和编程只在能明确关联失业、收入、责任、被骗、隐私或家庭生活时进入常规选题。
- 技术内容保留为差异化深度栏目，包括编程、Agent、MCP、工具治理与安全，但不作为默认入口。
- 选题应同时具备高频痛点、冲突角度、可验证证据和可复制资产。
- 纯产品发布、普通人无明显感知、没有行动价值的信号优先降级或停止写作；不得用夸张情绪弥补价值不足。
- 默认服务大众读者；标题必须让不了解具体工具和技术背景的人立刻理解个人影响并愿意继续确认答案。
- 常规标题不以版本号、类名、配置项、斜杠命令或内部 API 开场，阅读前置知识不超过 2 项。
- 写作前必须形成逐结论证据契约；一个笼统的“已人工确认”不能支持整篇文章。
- 官方 Release 只能写版本解读、迁移清单和待验证风险；实测、教程、故障复盘和工具横评必须有对应运行材料。
- 工具横评必须统一任务、上下文、规则和验收标准。
- 建议内容配比：35% 工作与收入、25% 钱/消费/诈骗、25% 健康/家庭/教育/情绪/生活、15% 技术深度。
- 缺少最低证据时停止写作，不允许模型自行补造。

## 事实与安全

- “实测”“提升”“降低”等结论必须附验证方法与结果。
- 工具功能、价格、版本和平台规则必须记录来源与核验日期。
- 只使用自建 Demo 或不可逆脱敏案例，不出现公司源码、业务数据、密钥和内部域名。
- 引用保留出处，不改写或拼接他人文章冒充原创。
- 文末参考资料使用 Markdown 有序列表，保留标题、链接、来源方及必要的发布日期；禁止使用 Markdown 表格或 HTML 表格，不展示“核验于 YYYY-MM-DD”，核验日期仅保留在内部结构化记录中。

## 视觉规范

- 固定使用深蓝 + 青绿色专业极简主题，整篇配色不超过 3 种。
- 正文 16px、1.8 行高；二级标题 19～20px，三级标题 17px。
- 每段控制在手机端 2～4 行，每 2～3 屏安排一个承担解释、证据或节奏作用的视觉节点。
- 优先使用流程图、迁移清单、结论卡和真实截图，不添加与内容无关的装饰图。
- 单个代码块尽量不超过 20 行，只保留解释结论所需的核心代码。
- 运行结果、性能数据和产品界面只能使用真实截图；无证据时保留明确占位，不得生成伪造截图。
- 正文字体遵循微信默认字体，不依赖 webfont；封面与模板图片使用可商用或系统字体。
- 封面、信息卡和正文配图保持同一标题安全区、品牌名和主题色。
